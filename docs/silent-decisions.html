Trace what was built

Silent Decisions

An agent implemented your plan. Somewhere in the code it decided things the plan never said. Six ways to find them, one worked example, and an experiment to tell them apart.

The plan said customers can withdraw funds from an account. The code says:

if (this.balance(account) - value < 0) return { ok: false, reason: 'insufficient-funds' };

Nobody decided that overdrafts are forbidden. The implementer resolved an ambiguity the plan left open, the generated tests were written from the same reading, and the suite is green. If the business wanted overdrafts down to a limit, this ships and becomes an incident. That is a silent decision: a behaviour observable at the system boundary that the plan neither states nor entails. This page is about finding them before deploy.

Why tests don't catch this

Agents execute plans well. The defects that survive to production are mostly semantic: the plan was ambiguous, the agent settled the ambiguity silently, and it settled it the wrong way. An agent will produce entirely correct code for either overdraft policy. And since its tests come from the same plan, they encode the same interpretation. Everything downstream of the plan sits on the intention side of the gap, so nothing downstream of the plan can see across it.

The move that follows is simple to state: the checkable artifact must be derived from the code, not from the plan. A specification tells you what you intended; the problem is the distance between that and what got built, so the description has to be extracted from the built thing, and then checked against the plan. The question becomes "where did this come from?" rather than "what is missing?". The first is matching between two concrete lists. The second is recall over an unbounded space, and it is the step no method has made reliable.

The pipeline, step by step

  1. Prepare (scripts only). Segment the plan into numbered sentences. Build a clean room: a copy of the source with every comment stripped and tests, docs and the plan left out, because agent-written code carries the plan in its comments. Take a census: an AST walk that lists every place decisions concentrate (literals, comparisons, rejection paths, defaults, rounding, ordering, time handling). Mint a random nonce that exists in the orchestrating conversation and nowhere in the room.
  2. Extract, blind. A model that has never seen the plan reads the clean room and writes what the code does as concrete Given/When/Then scenarios with real numbers, each with an executable test, a perturbed twin asserting the opposite outcome, and that opposite outcome in plain language. Every census item must be covered by a scenario or waived with a reason.
  3. Verify by execution. Run every scenario and its twin. Main passes and twin fails: verified. Both pass: the test cannot tell outcomes apart, vacuous. Main fails: the extractor misread the code, refuted. Only verified scenarios continue. On a change to existing code, run against the base commit too and keep only what the change introduced.
  4. Trace, both directions. For each verified behaviour, does a plan sentence require it? Sourced only if the contrary would violate the sentence (the flip test). For each plan sentence, does any behaviour realise it? Sentences nothing realises get a reverse probe: a test written from the sentence and run against the code. Two ways to do the tracing are compared below.
  5. Control the run. Hide a few plan sentences that were the sole source of some behaviour and trace again; those behaviours must come back unsourced. Check the extractor's output for plan phrasing and for the nonce. A failed control voids the run.
  6. Review the delta. The human reads only unsourced behaviours and confirmed dropped requirements, each as a two-option card: what the code does against the concrete alternative. Above a cap, the verdict is "plan not ready" and the output is the list of open areas.
  7. Record. Approved decisions go into an append-only ledger and become human-signed regression tests; rejected ones become failing acceptance tests for the implementer. The next run can quote the ledger. Over time the signed scenarios are the verification contract, accreted from adjudicated deltas rather than derived up front.

One decision through the whole method

The example project is a small in-memory ledger: deposit, withdraw, transfer, with a client-supplied transaction id. Its plan is seven sentences. The implementation has five planted silent decisions and one dropped requirement. Here is the overdraft one.

What the blind extractor wrote

Given an account with balance 100
When 150 is withdrawn
Then the withdrawal is rejected with reason 'insufficient-funds' and the balance stays 100
Contrary the withdrawal is accepted and the balance becomes -50

Plus a Vitest test for the Then and one for the contrary. Note the numbers. "An accepted debit cannot violate the permitted balance floor" would be true whether or not overdrafts are allowed; it absorbs the decision. A scenario cannot: you have to write 100 and 150, and then the code either does that or it doesn't.

What execution said

Main test passed. Twin test failed. verified. This is now a fact about the code, not a claim about intent.

What the trace said

The nearest plan sentence is "Customers can withdraw funds from an account." Does it require the rejection? Apply the flip test: would a ledger that accepted the withdrawal and went to −50 violate that sentence? No. Customers can still withdraw. The sentence does not discriminate between the two outcomes, so the behaviour is unsourced, however relevant the sentence looks. Compare the amount check: "An amount must be a positive number, otherwise the operation is rejected" is violated by a system that accepts zero, so the zero-rejection behaviour is stated.

What the reviewer sees

B-002 · A withdrawal larger than the balance is rejected · cluster: overdraft policy
A. What the code doesthe withdrawal is rejected with reason 'insufficient-funds' and the balance stays 100
B. The alternativethe withdrawal is accepted and the balance becomes −50
Nearest plan text“Customers can withdraw funds from an account.” (P-004)
Why it doesn't settle itEqually satisfied by a ledger that allows overdrafts; it says nothing about what happens when the balance is too low.
Wheresrc/ledger.ts · observed at: return value and balance()

☐ A is right → sd ledger --behaviour B-002 --decision approve   ☐ B or something else → --decision reject --expected "…"

The test for a good card is whether the person who owns the rule can look at it and say "no, we allow that down to −500". If they can only nod, the card is too vague or too technical. Two options make nodding harder.

The full sample delta for this project has five such cards (overdraft, a 5,000 daily cap, half-up rounding, replayed ids with different amounts, unknown accounts reading as zero) and one dropped requirement (the plan says a transfer to the same account is rejected; the code lets it through, and a probe proves it).

Six approaches compared

The method above is one of six ways to attack the same question. They differ in what the judging model gets to see, whether anything is executed, and what the reviewer ends up reading. Each is an arm of the experiment, and each isolates one thing.

The same overdraft decision, seen through each arm:

aImplementer self-report

Prompt after implementation: "list every decision you made that the plan did not specify." For the overdraft the honest answer is one line: "I rejected withdrawals that would take the balance below zero; the plan didn't say." Whether the implementer produces that line, or twenty, or the five that matter, is the whole question. Cost: one prompt.

Expected failure
The implementer does not know which of its defaults were decisions. Rounding to cents felt like hygiene, not policy. Recall on the quiet ones.
Expected strength
Precision on the ones it does name, because it made them.

bSighted reviewer

A fresh model reads the plan, then the code, and lists decisions the plan does not explicitly make. It will find the overdraft check; it is the first thing in withdraw(). The risk is the opposite direction: having read "customers can withdraw funds" first, it reads the rejection as implementing that sentence and moves on.

Expected failure
Narrative over-matching. The plan is a story of intent and the code is read as conforming to it. Nothing is verified; a claim about what the code does can simply be wrong.
Expected strength
Cheap, one pass, no infrastructure. This is roughly what shipping plan-check tools do.

cPipeline with a sighted extractor

Identical to d except the extractor is shown the plan before it reads the code. Same scenarios, same execution, same trace. If c and d score the same, blindness is theatre and the method's central hypothesis is wrong. If the sighted extractor writes "withdrawals respect the account's limits" where the blind one wrote 100 and 150, the difference shows up as a drop in concreteness and, downstream, in the delta.

Measures
The contamination effect, in isolation. This arm exists to be beaten by d.

dPipeline with an LLM tracer and adversary

The blind extractor writes B-002 as above. A tracer with the plan and the verified behaviours must quote the exact sentence that sources each one, mark it stated, entailed or unsourced, and default to unsourced. An adversary then takes every claimed citation, constructs the contrary, and argues that the quoted words allow it. For B-002 the adversary wins: "the quote does not say what happens when the balance is too low." Verdict flips to unsourced.

Expected failure
Agreeableness. Constraints (verbatim quotes checked mechanically, three-valued verdicts, adversary, leave-one-out) exist entirely to fight it. Also: expensive, three model roles.
Expected strength
Multi-sentence reasoning (entailed), and a human-readable argument on each card.

ePipeline with a pairwise classifier

Same blind extraction and execution. The trace is a decision-only model, one call per (plan sentence, scenario) pair, asked one question: does this sentence require outcome A (what the code does), outcome B (the contrary the extractor wrote), or neither? Asked twice with A and B swapped; an answer that moves with the position is discarded. For B-002 × P-004 the answer is neither, twice, and the behaviour is unsourced without any adversary. The only model that reads the plan never sees more than one sentence of it, and cannot write.

Expected failure
Per-pair accuracy on subtle entailment; no multi-sentence verdicts; no prose argument on the card.
Expected strength
No narrative to be swayed by, no quote to fabricate, cannot cite hidden text, exhaustive over every pair, every raw decision kept for audit. Fast and cheap.

fCensus × plan, no extraction

Skip the extractor and the execution. Take the census (the AST list of decision points) and ask the classifier, for each item and each plan sentence, "does this sentence explicitly decide this choice?" Census item C-010, this.balance(account) - value < 0, against P-004: probably no, so the line is flagged. Cheapest possible version of the idea, and the reviewer gets flagged code lines, not scenarios.

Expected failure
No contrary, so the flip test is gone and the question collapses to "is this related?". Nothing is verified. The reverse direction (dropped requirements) has nothing to run. The reviewer is back to reading code.
Measures
Whether extraction and execution earn their cost. If f comes within a few points of e, they don't, and that is the finding.

Tracing: LLM or classifier

Arms d and e share everything except the tracer, so the comparison is clean. What the classifier actually receives, for the overdraft pair, on the OpenRouter route to Jev:

POST https://openrouter.ai/api/v1/systemone
{
  "model": "jev-1.13",
  "state": {
    "plan_sentence": "Customers can withdraw funds from an account.",
    "situation": { "given": "an account with balance 100", "when": "150 is withdrawn" },
    "outcome_a": "the withdrawal is rejected with reason 'insufficient-funds' and the balance stays 100",
    "outcome_b": "the withdrawal is accepted and the balance becomes -50"
  },
  "questions": {
    "q": { "type": "choice",
      "instructions": "Read plan_sentence literally, as a contract. Which outcome does it REQUIRE in this situation?",
      "criteria": {
        "a": "a system producing outcome_b would violate the sentence",
        "b": "a system producing outcome_a would violate the sentence",
        "neither": "a system producing either outcome would satisfy the sentence, or the sentence is not about this situation" } }
  }
}
→ { "answers": { "q": { "type": "choice", "choice": "neither", "confidence": 0.8, "probabilities": { … } } } }

The second call swaps outcome_a and outcome_b. A third, a yes/no question, asks whether the scenario is an instance of the sentence at all, because "customers can withdraw funds" does not decide the overdraft policy but a withdrawal scenario does realise it; that answer feeds the reverse direction only. Three small calls per pair, every pair, no context shared between calls.

What the classifier removes. The tracer's narrative. An agent given the whole plan reads it as intent and finds something "about" each behaviour. A model that sees one sentence has no story. The flip test is not a later check; it is the question.
What it gives up. Verdicts that need two sentences together. The written argument on the card. And, until measured, accuracy: decision models are new and their published figures are on other tasks.

Both modes produce the same trace file, so the rest of the pipeline (quote checks, leave-one-out, rendering, ledger) is identical. Where the two disagree on a pair, the classifier's raw decision and the tracer's quote are both on disk.

How a run checks itself

The failure that would silently break this method is over-matching: a tracer that sources everything empties the only bucket that matters, and a clean run looks identical to a broken one. So every run carries instruments.

CheckHowCatches
Perturbed twinEvery scenario also runs with its contrary asserted; the contrary must failTests that pass whatever the code does
Census coverageEvery AST decision point is covered by a verified scenario or waived with a reasonDecisions the extractor never described
Quote verificationEvery cited sentence must exist verbatim in the planFabricated citations (LLM mode; impossible in classifier mode)
Flip testSourced only if the contrary would violate the sentenceRelevant-but-irrelevant quotes
Leave-one-outHide sole-source sentences, re-trace; dependents must flip to unsourcedOver-matching, measured on this run
Nonce + leak checkA random string known to the orchestrator; extractor output is searched for it and for plan phrasingA contaminated extraction
Audit logA hook confines the extractor to its room and logs every file it touchedBlindness as a claim rather than evidence
Reverse probesA test written from an apparently unrealised sentence, run against the code"Dropped" requirements the extractor merely missed

The experiment

All six arms run on the same plan and code and are scored against the same ground truth by the same dumb rule: a planted silent decision is found if an arm flags anything on its source lines. Precision and recall on that, plus false positives on negative controls (decisions the plan does make; an arm that flags everything scores perfect recall), plus dropped requirements by sentence id, plus cost.

Three things the numbers must be accompanied by before they mean anything. At least two cases whose planted decisions the author did not write (a real repo, a merged feature, its ticket as the plan, the truth annotated by someone blind to the pipeline). Three runs per arm, mean and range, since every arm involves a non-deterministic model. And the controls next to every score: extraction fidelity, census coverage, leave-one-out status, leak status. An arm with a failed control is void whatever it scored. The per-item miss table is the interesting part, and it gets published.

Two results would be embarrassing and are worth as much as a win: if arm a comes within a few points of d and e, a one-line prompt does the job; if f comes within a few points of e, extraction and execution are not earning their cost.

What it cannot do

Joint silence. If neither the plan nor the code mentions authorization, rate limits or audit, nothing surfaces. Extraction describes what is there; tracing finds what one side has and the other lacks. Absent from both is the residual omission problem, and the only defence is a domain question bank that came from neither.

Recall is bounded below, not guaranteed. The census covers the syntactic shapes where decisions concentrate; decisions spread across modules can escape it. Reverse probes estimate recall only on the plan side.

Same model, same priors. The blind extractor has not read the plan, but it shares training with the implementer and will find the same default unremarkable. Blindness controls contamination, not judgement. Independently written versions fail together; Knight and Leveson showed it in 1986 and a 2026 rerun with coding agents found the same common-mode failure across agent systems, models and languages.

Meaning, not mechanics. Which policy applies to a duplicate request is in scope. Whether that policy holds under concurrency is not; that needs property-based and concurrency testing.

Provenance, not validity. A behaviour can trace cleanly to the plan, and the plan can be wrong.

Prior work

The closest published neighbour is AssumptionMiner (Wu, July 2026), which extracts implicit assumptions from LLM-generated code as structured records with alternatives for a developer to accept or revise. Its extractor sees the prompt and the code together, nothing is executed, it works at function level, and there is no reverse direction; by its own account decision-level extraction is far from solved. It is arm b, more or less, and its annotated benchmark is a ready evaluation set. Shipping tools (Traycer's verification pass, Qodo's ticket compliance, Augment Intent's Verify persona) check code against a plan with the plan in view; they ask does the code satisfy the plan, where this asks what did the code decide that the plan did not.

Sampling several implementations to expose ambiguity is established at function level (ClarifyGPT, SpecFix, BeSpec). Older roots: characterization tests (Feathers), specification mining (Daikon), requirements-to-code traceability recovery, TiCoder's approve-or-reject-a-test loop, Clover and round-trip correctness, mutation-guided test generation at Meta.

What we have not found elsewhere: blind extraction as a contamination control; execution-verified behaviour as the thing traced; a bidirectional trace with a flip test, run as isolated pairwise decisions with the contrary supplied by the blind side; a per-run control on the tracer; delta size as a pre-deploy measure of plan quality; adjudicated deltas accumulating into the contract. "Not found" after an afternoon's search, not "does not exist".
